1. Visão geral

O servidor do trabalho é na verdade um grupo de N processos (S1, S2, ..., SN) que entram no mesmo grupo multicast. Cada um conhece o id, o IP e a porta dos outros, que ficam no config.json. O cliente manda a requisição para o endereço do grupo, então todos os servidores recebem, mas só quem é o líder responde. O líder é o servidor sem falha com o menor id. Na resposta vai o resultado e também o id, o IP e a porta de quem atendeu.

Para saber quem está vivo, cada servidor manda um heartbeat no grupo a cada 0,5 s. Se um servidor fica 1,5 s sem mandar heartbeat, os outros consideram que ele falhou. Só tratamos falha por parada total; nos testes matamos os processos com kill -9. Como a troca de líder leva por volta de 1,5 s, ela termina antes do cliente desistir de esperar (ver cenários 3 e 11).

Fizemos em Python 3 usando só a biblioteca padrão (socket, threading e json). Rodamos 15 cenários de teste e as 92 verificações deram certo (92 de 92).

Escolhemos conta bancária porque se uma escrita for executada duas vezes dá para ver na hora (o depósito aparece em dobro), o que ajuda a mostrar nos testes que isso não acontece.

3. Arquitetura

Dividimos o código assim:

  • comunicacao.py: sockets UDP, envio/recebimento em JSON e entrada no grupo multicast;
  • conta.py: saldo, cache de requisições já feitas, versões e cópia do estado;
  • membros.py: guarda os heartbeats recebidos e calcula quem está vivo e quem é o líder;
  • servidor.py: o protocolo em si (requisições, replicação, sincronização);
  • cliente.py: manda as requisições e reenvia se não vier resposta.

Cada servidor roda quatro threads:

ThreadFunção
heartbeatmanda HEARTBEAT no grupo a cada 0,5 s
monitora cada 0,2 s recalcula os vivos e o líder e escreve no log quando algo muda
gruporecebe o que chega pelo multicast: HEARTBEAT, REQ, REPLICA e SYNC_REQ
unicastrecebe na porta do servidor os ACK e o STATE

A eleição não usa mensagens próprias. Como todos recebem os mesmos heartbeats, cada servidor calcula lider = min(vivos) e, quando chega uma requisição, vê se ele é o líder ou não.

4.1 Escrita

  1. O cliente manda REQ para o grupo, com um req_id único.
  2. O líder executa a operação.
  3. O líder manda REPLICA para o grupo.
  4. Cada réplica executa e manda ACK para o líder.
  5. O líder espera o ACK de todos que ainda estão vivos. Como UDP pode perder pacote, ele reenvia a REPLICA a cada 1 s. Se uma réplica morre no meio, ela sai da lista de vivos e o líder para de esperar por ela.
  6. O líder responde ao cliente dizendo em quais servidores a escrita ficou.

Consultas o líder responde direto. As escritas passam por um lock no líder, uma de cada vez, e por isso todas as réplicas aplicam na mesma ordem.

4.2 Falha do líder

Entre a morte do líder e a detecção, ninguém responde: o líder está morto e os outros ainda acham que são réplicas. Para não perder as requisições que chegam nesse intervalo, as réplicas guardam a requisição por um tempo (timeout + 1 s). Se uma delas virar líder, atende na hora o que guardou. Além disso o cliente reenvia a mesma requisição (mesmo req_id) a cada 0,5 s. Nos testes a resposta chegou uns 2 s depois da queda do líder.

5. Decisões que tomamos

  • O cliente reenvia sempre com o mesmo req_id. Ele espera no total 12 s (6 tentativas de 2 s) e reenvia a cada 0,5 s. Isso cobre o tempo da troca de líder e também perda de pacote.
  • As réplicas guardam a requisição durante a troca de líder (explicado na seção 4.2). Quando o líder está normal, essa cópia só expira.
  • Para não executar a mesma escrita duas vezes, cada servidor guarda um cache req_id → resultado. Se o líder morre depois de replicar e antes de responder, o novo líder já tem aquela escrita no cache e só devolve o resultado (cenário 9).
  • Quando um servidor acabou de subir ele ainda não sabe quem está vivo, então nos primeiros 1,5 s ele não atende cliente. Senão ele poderia achar que é o líder.
  • Quando um servidor volta de uma falha, ele manda SYNC_REQ e o servidor vivo de menor id que já tem estado responde com STATE. Só depois disso ele pode virar líder (cenário 10). O campo sinc do heartbeat diz quem já tem estado; se ninguém tem, todos começam com saldo 0.
  • Cada escrita tem um número de versão. A réplica só aplica a próxima versão; se receber uma versão velha ela manda ACK sem mudar nada. Assim uma REPLICA atrasada não volta o saldo para trás.
  • Se alguma réplica viva não confirmar em 8 s, o líder responde com ok=false e REPLICACAO_NAO_CONFIRMADA. Não respondemos sucesso sem ter os ACKs.
  • Réplica que ainda não recebeu o estado não aplica escritas, e um STATE mais velho que o estado atual é ignorado. Os cenários 13 e 14 testam escrita enquanto S2 ou S3 estão voltando.
  • Na primeira versão tinha um erro: o servidor que voltava de uma falha virava líder com saldo 0. Achamos pelo cenário 10 e corrigimos com a sincronização acima.

6. Como executar

# um servidor em cada host (os IPs ficam no arquivo de config)
python3 servidor.py --id 1 --config config_lab.json --log logs/s1.log
python3 servidor.py --id 2 --config config_lab.json --log logs/s2.log
python3 servidor.py --id 3 --config config_lab.json --log logs/s3.log

# cliente, em qualquer máquina da mesma rede (--iface = IP dessa máquina)
python3 cliente.py SALDO --config config_lab.json --iface 10.17.110.6

python3 cliente.py --config config_lab.json --iface 10.17.110.6    # modo interativo

# derrubar um servidor (parada total)

# cenários numa máquina só (3 processos em 127.0.0.1)

# cenários nos 3 hosts (rodado no macalan, com ssh para orval, cpu1 e cpu2)
python3 cenarios_lab.py --iface 10.17.110.6 --saida logs/lab

# gerar esta página
python3 gera_pagina.py --logs logs/pos_correcoes --lab logs/lab

7. Testes

Para testar fizemos o cenarios.py, que usa UDP e multicast de verdade. Em cada cenário ele sobe os servidores, manda requisições com o cliente, mata processos com kill -9 e confere qual servidor respondeu e qual o saldo. No final confere se o saldo é o mesmo em todas as réplicas vivas. Para cada cenário ficam os logs de cada processo, o roteiro do que foi feito e uma linha do tempo com todos os logs juntos em ordem de horário.

Nos cenários 8 e 9 quem faz o processo parar é ele mesmo (os._exit, com a opção --falha), porque precisávamos que ele parasse num ponto exato do protocolo e com kill na mão não dá para acertar o momento. Para os outros processos é igual a uma parada total.

9. Limitações

  • Só tratamos parada total, como pede o enunciado. Se a rede se dividir, cada lado vai eleger um líder.
  • Se heartbeats se perderem, por um instante dois servidores podem achar que são líder. O cliente usa a primeira resposta e descarta a outra pelo req_id.
  • O saldo fica só na memória. Se todos os servidores caírem, o estado se perde (cenário 12).
  • Se der o timeout de 8 s da replicação, o cliente recebe erro, mas a escrita pode ter sido aplicada no líder e em parte das réplicas.
  • Se uma réplica perder várias REPLICA seguidas e ficar com um buraco nas versões, ela para de confirmar. Não fizemos ressincronização automática para isso; é preciso reiniciar o processo.
  • O multicast tem TTL 1, então todas as máquinas precisam estar na mesma rede local.
